# TODO: проверить runtime-семантику skill metadata в DSH

**Статус:** OPEN  
**Тип:** внешняя зависимость / задача для DSH  
**Владелец технической проверки:** DSH  
**Потребитель результата:** AIP Mirror — AI-infrastructure integration

## Цель

Установить по первичным техническим источникам и воспроизводимым проверкам, как актуальная версия DSH обрабатывает skill metadata и как эти механизмы должны учитываться при интеграции в AIP Mirror. Эта запись отслеживает внешнюю техническую работу; она не означает, что DSH уже подтвердил перечисленные ниже поведения.

## Вопросы для проверки

1. Как DSH обрабатывает `whenToUse`: влияет ли поле на discovery, ранжирование, выбор skill, автоматическое invocation или только на описание/подсказку?
2. Какова точная runtime-семантика `disable-model-invocation`?
3. Какова точная runtime-семантика `user-invocable`?
4. Какие выводы относятся к текущей версии DSH, какие — к конкретным историческим версиям/экспериментам, а какие остаются неопределёнными?
5. Какие из подтверждённых механизмов являются DSH-specific, а какие можно безопасно отражать как общие правила интеграции AIP Mirror?

## Требуемые evidence

- Точная версия/ревизия DSH и среда выполнения, в которой проводилась проверка.
- Ссылки на первичные исходники, документацию или соответствующие участки реализации.
- Воспроизводимые тесты для каждого проверяемого поведения: входные metadata, setup, действия, наблюдаемый результат и ограничения теста.
- Отдельное обозначение документированных гарантий, наблюдений, гипотез и неразрешённых вопросов.
- Явная фиксация того, что именно проверено; чтение поля в документации само по себе не считается доказательством runtime-поведения.

## Критерии завершения

- Для `whenToUse`, `disable-model-invocation` и `user-invocable` опубликованы проверяемые выводы с версионной областью действия.
- Для утверждений о runtime-поведении приложены первичные источники и/или воспроизводимые результаты тестов.
- Неопределённость и ограничения evidence явно сохранены; предположения не представлены как подтверждённые факты.
- Результаты переданы для интеграции в AIP Mirror. Интеграционные изменения выполняются отдельно в соответствующих canonical owners и документации AIP Mirror.
- После получения результатов AIP Mirror обновляет только те интеграционные правила и пояснения, которые подтверждены evidence; эта внешняя задача закрывается отдельно от документационного TODO AIP Mirror.

## Граница ответственности

- **DSH:** техническая точность описания реализации и runtime-поведения DSH, версия тестируемой среды и evidence.
- **AIP Mirror:** интерпретация подтверждённых сведений для собственной архитектуры, semantic ownership, activation/workflow rules и документации интеграции.
- Не приписывать DSH неподтверждённое поведение и не смешивать отсутствие локального теста с доказательством отсутствия механизма.
