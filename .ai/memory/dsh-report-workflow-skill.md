# Отчёт DSH: `.ai/skills/workflow/SKILL.md`

**Статус:** CLOSED for the recommendations below — применено в владельце (см. «Что применено»)  
**Тип:** анализ пригодности canonical owner для Agentic AI  
**Владелец технической проверки:** DSH (Agentic AI, локальный git)  
**Потребитель результата:** AIP Mirror — AI-infrastructure  
**Проанализированный материал:** `.ai/skills/workflow/SKILL.md`, редакция `a0fbc8d`  
**Область действия:** среда DSH с локальной рабочей копией git; версии указаны в каждом пункте

## Что это за документ

Отчёт о том, как скилл `workflow` выглядит **с точки зрения агента, работающего с
локальным git-репозиторием**. Скилл создавался для Conversational AI, который
читает репозиторий через GitHub API. Разделы 1–8 — это общая методология, и она
в основном хороша. Раздел 9 написан целиком под API и для меня неприменим.

Этот документ — рабочий контекст, а не новый semantic owner. Если он расходится с
`.ai/skills/workflow/SKILL.md`, владелец главнее.

## Краткий вывод

Методологическая часть (§1–§8) полезна и переносима: она не зависит от того, как
именно агент читает и меняет файлы. Проблема сосредоточена в §9: процедура
«authoritative, pinned tree snapshot» описывает доступ через API, который у меня
отсутствует, и подменяет более простую и более надёжную локальную операцию.

Отдельно: **§9 ссылается на путь, которого больше нет** (`.ai/docs/architecture/*`).
Это фактическая ошибка, независимая от host-модели.

## 1. Что полезно и должно остаться

| Место | Почему полезно |
|---|---|
| §1 general cycle | research → document → review → specify → prototype → validate → implement → test → document. Работает независимо от host |
| §2 research before implementation | «implement only after the understanding is sufficiently reliable» — прямо то, что нужно агенту с доступом к записи |
| §3 validate behaviour | классификация observed fact / inference / assumption / open question до промоушена в спецификацию |
| §4 small reviewable changes | инкрементальность; снижает цену ошибки |
| §5 testing at the lowest level | не поднимать Illustrator ради чистой функции — верно и для меня |
| §6 commits | ссылка на владельца commit-политики, без дублирования |
| §7 documentation follows decisions | решения не должны жить только в чате |
| §8 lightweight | «AI instructions SHOULD help development rather than become development overhead» |
| §9 идея «не доверять неполному индексу» | сам принцип верен, вопрос только в исполнении (см. §2 ниже) |

## 2. Что вредно или неприменимо — по пунктам

### 2.1 §9: процедура на 7 шагов описывает API, а не мою работу

Ключевая проблема файла. Скилл предписывает:

> 1. Read the Git ref … (for example, `GET /repos/{owner}/{repo}/git/ref/heads/main`) …
> 3. Request the recursive tree for that exact tree SHA
> 5. Treat the tree as complete only when `truncated` is `false`

**Проблема.** У меня нет `GET`, нет `truncated`, нет recursive tree. У меня есть
локальный git, где та же задача решается двумя командами и **вообще не может
быть усечена**.

**Доказательство:**

```
git rev-parse HEAD          -> a0fbc8d385b40378b2c676cc2d1a2318d68f0833
git rev-parse 'HEAD^{tree}' -> 76ce3e62fb06ea1bb27a606c09d78ef8d342c68f
git ls-tree -r HEAD --name-only | count -> 219
```

`git ls-tree -r` отдаёт **полное** дерево. У него нет параметра page/limit, нет
флага `truncated`, и он не может вернуть половину. Вся конструкция из шагов 1–7
(обойти усечение, доказать полноту, зафиксировать статус) существует **только
из-за ограничений API**. Для меня это лишняя процедура, которая:

- предписывает мне инструмент, которого у меня нет;
- заменяет одну локальную команду семью шагами;
- создаёт впечатление, что полнота дерева «доказывается», тогда как локально она
  просто дана.

**Что делать.** Разделить §9 на два: «локальная инспекция (Agentic AI)» и
«удалённая инспекция (API)». Сам принцип — «не выводить полноту из подозрительного
индекса» — сохранить, но привязать к правильному механизму.

### 2.2 §9: ссылка на несуществующий путь

Пример батчинга в §9 указывает на каталог, которого в репозитории нет.

**Доказательство:**

```
.ai/docs/architecture/*    -> False (не существует)
.ai/docs/                  -> плоский: 7 .md + README.md, без подкаталогов
```

Фактическое содержимое `.ai/docs/`:

```
adapting-to-a-new-project.md
agentic-ai-dsh-observations.md
agentic-ai-skill-discovery-verification.md
ai-document-hierarchy-and-authoring.md
ai-infrastructure-context-mode.md

```

Каталог `architecture/` был уплощён (это видно и по `.ai/docs/README.md`, который
перечисляет документы плоско). Скилл сохранил старый путь. Для агента, который
использует этот список как **инструкцию к чтению**, результат — попытка прочитать
несуществующий каталог.

### 2.3 §9: список батчей не покрывает реальную структуру

Даже по составу список неполон. Сравнение с фактом:

| Путь из списка §9 | Существует | Комментарий |
|---|---|---|
| `.ai/config.yaml` | да | — |
| `.ai/docs/architecture/*` | **нет** | каталог уплощён |
| `.ai/skills/*` | да | — |
| `.ai/conversation-management/*` | да | — |
| `.ai/handoffs/README.md` | да | — |
| `docs/PROJECT-INSTRUCTIONS.md` | да | — |

Не упомянуты: `.ai/README.md`, `.ai/AGENTS.md`, `.ai/INDEX.md`, `.ai/memory/`,
`.ai/scripts/`, `.ai/tests/`. Для «семантического обхода активного слоя» это
существенные пропуски: например, `.ai/memory/` — это активный рабочий контекст, а
`.ai/scripts/` содержит исполняемые инструменты инфраструктуры.

### 2.4 §9: смешение двух моделей репозитория в одном разделе

Раздел начинается с абстрактного принципа («prefer the repository's authoritative
tree/contents API»), затем переходит к API-процедуре, затем — к общей идее
батчинга. Три разные вещи в одном тексте:

1. принцип «не доверять неполному индексу» — нужен всем;
2. процедура pinning через API — только Conversational AI;
3. батчинг больших выборок — нужен обоим, но по-разному реализуется.

Из-за смешения невозможно понять, какой шаг обязателен для меня. Это тот же
дефект, что и в `repository/SKILL.md`: отсутствует адресат у host-specific части.

### 2.5 Мелочь: ссылка на владельца без пути

```
§6: Follow `.ai/skills/commits/SKILL.md` for commit-message construction and
    the canonical repository owner for commit policy.
```

Для `commits` путь указан, для repository owner — нет. Ссылка «на словах» требует
поиска. Не вредно, но непоследовательно, и в файле, который читается агентом,
явный путь дешевле.

## 3. Чего не хватает

### 3.1 Локального варианта §9

Нужен эквивалент для агента с рабочей копией. Например:

```
git rev-parse HEAD                      зафиксировать ревизию
git rev-parse 'HEAD^{tree}'             зафиксировать корневое дерево
git ls-tree -r HEAD --name-only         полный список (усечение невозможно)
git status --porcelain --ignored        состояние рабочей копии
```

Последняя строка важна именно для меня: `git ls-tree` показывает **коммит**, а не
рабочую копию.

### 3.2 Правил про рабочую копию как отдельное состояние

У API-клиента «репозиторий» — это коммиты. У меня есть ещё:

- незакоммиченные изменения;
- staged-изменения;
- untracked файлы;
- **ignored** файлы, которых нет в git вообще.

**Доказательство, что это разные множества:**

```
git ls-files .agents             -> 0 entries
actual .agents/skills dirs       -> 9
git status --porcelain           -> 0 entries      (ignored невидим)
git status --porcelain --ignored -> 1 entry
```

Скилл требует «complete coverage of the declared scope», но не говорит, что
«scope» для локального агента шире, чем множество tracked-файлов.

### 3.3 Правил про деструктивные операции

§4 говорит про маленькие изменения, но нигде не сказано, что нельзя
«откатываться» через уничтожение работы. Проверка:

```
before: a.txt = 'PRECIOUS UNCOMMITTED'
$ git reset --hard HEAD
after : a.txt = 'committed'        ← работа потеряна
```

Для агента с рабочей копией это реальный риск, которого нет у API-клиента.
Инвариант «не терять существующую незакоммиченную работу» в скилле отсутствует.

### 3.4 Явного адресата

Как и в `repository/SKILL.md`: ни один раздел не помечен «для Conversational AI»
или «для Agentic AI». Формулировка «prefer … over …» не разграничивает
применимость, а предлагает выбор, которого у меня нет.

## 4. Что мне нравится

- **§3 validate behaviour.** Требование классифицировать находку до промоушена в
  спецификацию — прямо противоядие от поспешных выводов. Я сам опираюсь на этот
  принцип.
- **§2 research before implementation.** Уместно для агента, который может
  немедленно писать в репозиторий.
- **§8 lightweight.** «Instructions SHOULD help development rather than become
  development overhead» — хороший критерий для самих скиллов.
- **Принцип из §9** («do not infer completeness from a search index that is known
  or suspected to omit files») — верен; к нему стоит добавить, что локальный
  `git ls-tree` этой проблемы не имеет.

| Приоритет | Действие | Обоснование |
|---|---|---|
| Высокий | Разделить §9 по механизму: локальный git против API | §2.1; сейчас процедура требует отсутствующий инструмент |
| Высокий | Исправить путь `.ai/docs/architecture/*` | §2.2; каталога не существует — это фактическая ошибка |

| Низкий | Пометить адресата host-specific разделов | §3.4, §2.4 |
| Низкий | Дать явный путь к repository owner в §6 | §2.5 |

## 6. Границы этого отчёта

- Оценка сделана для среды **DSH с локальной рабочей копией git** и не
  претендует на роль инструкции для Conversational AI.
- Проверено на редакции `a0fbc8d`. При расхождении с текущим `SKILL.md`
  приоритет у владельца.
- Отсутствие `.ai/docs/architecture/` и состав `.ai/docs/` подтверждены
  командами этой сессии; цитаты — из прочитанного файла.
- Что именно изменится в владельце — решение пользователя. Документ фиксирует
  наблюдения и предложения, а не выполняет миграцию.
