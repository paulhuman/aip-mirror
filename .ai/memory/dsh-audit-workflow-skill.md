## 1. Краткое резюме

Методологическая часть (§1–§8) переносима и полезна: она описывает порядок
работы, а не механизм доступа к репозиторию. Проблема сосредоточена в §9.

**§9 целиком написан под remote API host.** Из двадцати двух строк раздела
шесть содержат API-лексику (`GET /repos/...`, `truncated`, `recursive tree`).
У DSH нет ни одного HTTP-инструмента из 38 доступных, зато есть локальный Git,
где та же задача решается **полностью и без риска усечения**.

**Найдена фактическая ошибка:** пример батчинга в §9 ссылается на
`.ai/docs/architecture/*` — такого каталога не существует. Документация
уплощена.

**Архитектурный вывод:** разделять skills не нужно, но host-механику следует
**вынести**, а не помечать. Проверено (на `repository`): при загрузке skill в
контекст уходит тело `SKILL.md` целиком, а соседние файлы skill — нет. §9
содержит ценный host-нейтральный принцип, который должен остаться, и 1 621 Б
API-механики (28 % файла), которая в контексте DSH бесполезна.

### 3.1 Эксперимент, подтверждающий локальный эквивалент §9

Проведено в целевом репозитории (только чтение):

```
git rev-parse HEAD                      -> c93e2e05abf37a5d2cc47befa0388a8cbf45824a
git rev-parse 'HEAD^{tree}'             -> корневое дерево получено
git ls-tree -r HEAD --name-only | count -> 219 записей
```

Ключевое отличие от API-пути: **усечение невозможно**. У `git ls-tree` нет
параметра страницы и нет поля `truncated`, поэтому шаги 4–5 процедуры для DSH
не имеют смысла. Вся конструкция «проверить, не усечено ли дерево» существует
исключительно из-за ограничений remote API.

## 5. Сравнение архитектурных альтернатив

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **A. Пометить host-подразделы маркером внутри §9** | Минимальная правка | **Проверено на `repository`: не работает.** При загрузке skill в контекст уходит тело `SKILL.md` целиком, маркер ничего не фильтрует | **Отклонено** |
| **B. Вынести API-механику в соседний файл skill** | Соседний файл не внедряется по умолчанию (проверено); связь с владельцем сохраняется | Защищает контекст, но не запрещает чтение по ссылке | **Рекомендуется** для API-механики |
| **C. Вынести host-механику вне `.ai/skills/`** | Защищает контекст **всех** host; совпадает с решением проекта о том, что механика host остаётся за пределами host-neutral правила | Требует явной маршрутизации | **Рекомендуется** для строго host-specific деталей |
| **D. Два skill: `workflow` + `workflow-host-dsh`** | Формальное разделение механизмов | `description` пересекаются по смыслу («workflow», «разработка») → недетерминированный выбор; два владельца одной методологии | Не рекомендуется |
| **E. `disable-model-invocation` на весь skill** | Механизм подтверждён | Скрывает skill **целиком**, включая §1–§8, нужные DSH; действует только на DSH | Не применимо |

**Обоснование выбора B + C.** §9 содержит один ценный host-нейтральный принцип:
«не выводить полноту из индекса, который может быть неполным». Он должен
остаться в теле, доступный всем host. При этом **реализации** этого принципа —
API-процедура (1 621 Б, 28 % файла) и локальные команды — являются механикой и
не должны попадать в контекст чужого host. Принцип остаётся, реализации
выносятся.

**Замер выигрыша.** `workflow/SKILL.md` = 5 732 байта. API-блок §9 занимает
1 621 Б (28 %). После выноса в теле остаётся принцип плюс локальный эквивалент.

**Почему не вариант E.** Проверено: `disable-model-invocation: true` убирает
skill из каталога и блокирует загрузку через tool, но скрывает **весь** skill.
Для `workflow` это означало бы лишить DSH методологии §1–§8, которая к host не
привязана. Поле пригодно для скрытия целого skill от одного host, но не для
разделения содержимого внутри файла.

## 7. Открытые вопросы и необходимые эксперименты

1. **Поведение remote API host не проверялось.** В этой среде нет ни такого
   host, ни HTTP-инструментов. Все утверждения о нём взяты из текста skill.
2. **Совместимость формулировок §9 с host, у которого есть и API, и локальная
   копия.** Такая комбинация не проверялась; возможно, раздел стоит строить не
   по host, а по «есть ли локальная копия».
3. **Полнота списка батчей.** Проверено, что перечисленные пути существуют, но
   не проверялось, покрывает ли список **весь** активный слой `.ai/`
   семантически.
4. **Version-sensitive.** Все выводы о DSH относятся к `0.2.0-rc.2`.
5. **Не проверено, как DSH ведёт себя при попытке выполнить API-инструкцию.**
   Наблюдалось только отсутствие подходящих инструментов, а не поведение при
   конфликте.
