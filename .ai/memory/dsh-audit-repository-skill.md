# Аудит DSH: `.ai/skills/repository/SKILL.md`

**Статус:** отчёт аудита  
**Тип:** независимый технический аудит skill против реальной среды исполнения  
**Аудируемый файл:** `.ai/skills/repository/SKILL.md`, редакция `c93e2e0`, 237 строк  
**Исполнитель:** DSH (Agentic AI, локальная рабочая копия Git)  
**Ограничение:** исходные файлы не изменялись; создан только этот отчёт

## 1. Краткое резюме

Skill выполняет две несовместимые роли одновременно. Разделы 1–3, 6, 6.1, 7 и 8
описывают **семантику проекта** и применимы к любому host. Но §8 и часть §7
содержат **процедуры конкретного host** (GitHub Contents API), которые к DSH не
применимы и в одном месте прямо опасны.

Главная находка: **§8 предписывает последовательность операций, которая в
локальной рабочей копии уничтожает незакоммиченную работу.** Проверено
экспериментально. Это единственный `HARMFUL` уровень в отчёте.

Второй по значимости факт: значительная часть §7 **уже внедряется DSH
принудительно**, независимо от skill. То есть эти инструкции для DSH
избыточны — но не бесполезны, потому что skill адресован нескольким host.

Архитектурный вывод: **разделять по metadata нельзя, а маркировать разделы
бесполезно.** Проверено, что при загрузке skill в контекст уходит тело
`SKILL.md` целиком, а соседние файлы skill — нет. Значит host-механику следует
не помечать, а выносить: в соседний файл skill или за пределы `.ai/skills/`.
Цель — не пускать инструкции одного host в контекст другого.

### 3.1 Эксперимент, подтверждающий §8

Проведён на одноразовом репозитории в `%TEMP%`, не на целевом:

```
before: a.txt = 'PRECIOUS UNCOMMITTED'
$ git reset --hard HEAD
after : a.txt = 'committed'          ← незакоммиченная работа потеряна
untracked survived: True             ← untracked при этом уцелел
```

Причина: у API-клиента нет незакоммиченного рабочего дерева, поэтому для него
подобная последовательность безвредна. У DSH рабочее дерево есть, и оно —
нормальное рабочее состояние. §8 этого различия не учитывает.

Проверено также, что изоляция решает проблему: `git worktree add --detach <path> <sha>`
создаёт отдельное рабочее дерево, и `reset --hard` внутри него **не затрагивает**
незакоммиченное изменение основного дерева.

## 5. Сравнение архитектурных альтернатив

### 5.1 Решающий факт: что именно попадает в контекст

Выбор архитектуры определяется одним проверенным свойством: **при загрузке skill
в контекст уходит тело `SKILL.md` целиком, а соседние файлы skill — не уходят.**

```
dsh-skill/lib/index.js:66   renderSkillContent → [name, resourceBase, skill.content]
```

Проба `zz-probe-res` — skill с двумя файлами:

```
SKILL.md           → "Main body marker: MARKER_IN_SKILL_MD"
host-mechanics.md  → "SIBLING MARKER: MARKER_IN_SIBLING_FILE"

загрузка skill через tool → в контексте присутствует только MARKER_IN_SKILL_MD
                            MARKER_IN_SIBLING_FILE отсутствует
```

Вывод, который опровергает рекомендацию первого выпуска этого отчёта:
**маркировка host-разделов внутри `SKILL.md` контекст не защищает.** Раздел
`### GitHub Connector-specific mechanics` (452 байта) при загрузке skill
внедряется в контекст DSH наравне с host-neutral инвариантами, потому что
отправляется всё тело файла. Поля `audience` в DSH нет (V13), фильтрации по
маркерам нет. Маркер виден только человеку.

### 5.2 Проверенные механизмы изоляции

| Механизм | Защищает | Доказательство |
|---|---|---|
| Соседний файл skill | Контекст **DSH** (не внедряется по умолчанию) | проба `zz-probe-res`: маркер соседнего файла в контекст не попал |
| Вынос за пределы `.ai/skills/` | Контекст **всех** host | проба `.dsh/skills/zz-probe-dshonly`: виден DSH, **не** виден через junction `.agents/skills` |
| Глубина > 1 | Контекст **DSH** | проба `.ai/skills/zz-probe-nest/inner/SKILL.md`: в каталоге не появился |
| `disable-model-invocation: true` | Контекст **только DSH** | skill отсутствовал в каталоге; tool вернул `not available for model invocation` |
| Маркировка `## Agent-only` | **Ничего** | тело внедряется целиком (строка 66 выше) |

**Асимметрия, существенная для задачи.** `disable-model-invocation` — поле DSH;
Connector читает `.ai/skills/<name>/SKILL.md` напрямую (V11) и метаданные не
применяет. Значит metadata защищает **один** host, а вынос по пути — **оба**.
Для цели «не пускать инструкции одного host в контекст другого» пригоден именно
путь, а metadata может служить лишь дополнением.

### 5.3 Сравнение альтернатив

| Вариант | Плюсы | Минусы | Оценка |
|---|---|---|---|
| **A. Маркировать host-разделы внутри тела** | Минимальная правка; один файл | **Проверено: не работает.** Тело внедряется целиком, маркер ничего не фильтрует | **Отклонено** |
| **B. Host-механика в соседних файлах skill** | Соседний файл не внедряется по умолчанию; сохраняется связь с владельцем; progressive disclosure | Защищает контекст, но не запрещает чтение: агент, которому нужна механика, прочитает файл по ссылке | **Рекомендуется** для механики, которая нужна редко, но не опасна |
| **C. Host-механика вне `.ai/skills/`** | Защищает контекст **обоих** host; совпадает с решением проекта: «правило сохраняет host-neutral инварианты, а *механика* каждого host остаётся за его пределами» | Требует явной маршрутизации для host, которому механика нужна | **Рекомендуется** для опасной и строго host-specific механики |
| **D. Два skill: `repository` + `repository-host-dsh`** | Формальное разделение | `description` пересекаются → недетерминированный выбор; два владельца одной темы; общие инварианты придётся дублировать | Не рекомендуется |
| **E. `disable-model-invocation` на весь skill** | Механизм подтверждён | Скрывает skill **целиком**, включая host-neutral инварианты, нужные DSH; действует только на DSH | Не применимо как основное решение |

### 5.4 Рекомендуемая композиция

Сочетание B и C, а не выбор одного:

1. **Тело `SKILL.md`** — только host-neutral инварианты: §1–§6.1, инварианты §7,
   принцип §8 («фикстуры не меняют каноническую историю»). Это то, что должно
   попадать в контекст любого host.
2. **Соседние файлы skill** — механика, нужная редко и не опасная: например
   полная процедура Connector по blob SHA.
3. **Вне `.ai/skills/`** — то, что не должно попасть в контекст чужого host
   вообще, включая destructive-рецепты. Прецедент в проекте уже есть:
   `.ai/conversation-management/handoff/SKILL.md` вложен намеренно, и
   `INDEX.md:36` прямо требует, чтобы эти владельцы не были обнаруженными
   skills.

**Замер выигрыша.** `repository/SKILL.md` = 10 920 байт; host-specific части:
§7 Connector 452 Б, §7 Agentic-host 650 Б, §8 фикстуры 1 484 Б. Все они сейчас
внедряются целиком.

### 5.5 Что подтверждено о metadata

`disable-model-invocation: true` убирает skill из каталога и блокирует загрузку
через tool; `user-invocable: false` влияет только на инъекцию по явному
упоминанию и **не** скрывает skill от модели. Оба - механизмы видимости всего
skill. Это делает их пригодными для скрытия целого skill от DSH (например,
Conversation-Management материала), но непригодными для разделения разделов
внутри одного файла.

## 7. Открытые вопросы и необходимые эксперименты

1. **Проверка §7 на практике.** Инварианты read-back/diff/scope не проверялись
   экспериментом в этой задаче из-за запрета менять исходники. Требуется
   отдельный прогон с намеренно повреждённым содержимым.
2. **Поведение при конфликте host-enforcement и skill.** DSH принудительно
   требует чтения перед записью. Что произойдёт, если skill предпишет обратное —
   не проверялось и в текущей формулировке skill не конфликтует.
3. **Другие host в этой среде недоступны.** Утверждения про GitHub Connector
   взяты из текста skill, а не из проверки. Проверить нечем.
4. **`prototypes/`.** Каталог существует, пуст и не отслеживается. Неясно,
