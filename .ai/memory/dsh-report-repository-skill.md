# Отчёт DSH: `.ai/skills/repository/SKILL.md`

**Статус:** CLOSED for the recommendations below — применено в владельце (см. «Что применено»)
**Тип:** анализ пригодности canonical owner для Agentic AI
**Владелец технической проверки:** DSH (Agentic AI, локальный git)
**Потребитель результата:** AIP Mirror — AI-infrastructure
**Проанализированный материал:** `.ai/skills/repository/SKILL.md`, редакция `a0fbc8d`
**Область действия:** среда DSH с локальной рабочей копией git; версии указаны в каждом пункте

## Что это за документ

Это отчёт о том, как скилл `repository` выглядит **с точки зрения агента, работающего
с локальным git-репозиторием**, а не через GitHub API. Скилл создавался для
Conversational AI, который видит репозиторий как удалённый объект и меняет его
через Contents API. У меня другой инструментарий, и часть инструкций либо
неприменима, либо вредна.

Этот документ — рабочий контекст, а не новый semantic owner. Если он расходится с
`.ai/skills/repository/SKILL.md`, владелец главнее.

## Краткий вывод

Разделы 1–6 и 8 написаны для модели «удалённый API», и в них есть прямые
инструкции, которые для меня **вредны**. Раздел 7 (write safety) наоборот —
самый ценный и почти полностью корректен. Смешение двух механизмов в одном
файле — главная проблема, и она решается не удалением, а разделением по
host-механизму.

Важно: скилл сам объявляет, что host-механизмы не должны в него попадать
(§7, «Agentic-host-specific mechanics»). То есть **самый ценный раздел уже
содержит правильный принцип**, но остальной файл ему не следует.

## 1. Что полезно и должно остаться

| Место | Почему полезно |
|---|---|
| §7 инварианты write safety | read → change → read back → verify → diff → scope → commit. Работает для любого механизма, включая мой |
| §7 «A successful write … does not by itself prove» | прямо запрещает мне рапортовать об успехе по факту успешного вызова инструмента |
| §6.1 граница owners/supporting | активный владелец не зависит от supporting-слоя. Полезно и применимо |
| §4 hygiene | секреты не коммитить — не зависит от host |
| §5 durability | репозиторий как durable record, а не чат |
| §2 external boundaries | reference-репозитории объявлены в config, а не копируются |
| §6 documentation traceability | решения не должны жить только в чате |

## 2. Что вредно или неприменимо — по пунктам

### 2.1 §1 Path resolution: «конструкция URL» вместо файловой системы

Скилл говорит:

> The canonical repository root is constructed from the configured hosting base URL
> and repository identifier.
> Do not resolve repository-relative paths from the current working directory …

**Проблема.** Для меня `cwd` — это и есть репозиторий. Локальный путь не
«конструируется» из `base_url`; он просто существует на диске.

**Доказательство:**

```
git rev-parse --show-toplevel   -> E:/Projects/repos/aip-mirror
git rev-parse HEAD              -> a0fbc8d385b40378b2c676cc2d1a2318d68f0833
```

Запрет «не резолвить от cwd» для меня неверен: локальный путь — первичен, а
`base_url` из `config.yaml` нужен только чтобы построить ссылку в тексте.

**Что делать.** Развести два случая: «как построить ссылку для документа» и «как
найти файл на диске». Второе — файловая система, первое — конфиг.

### 2.2 §8 Disposable repository fixtures: единственный реальный источник вреда

Самая опасная часть файла. Раздел предписывает создавать disposable branch,
менять файлы, проверять diff, и отдельно оговаривает:

> If moving an existing branch ref with `update_ref` is blocked, the AI MUST NOT treat
> that failure as evidence …

**Проблема 1 — терминология чужого механизма.** `update_ref` с подчёркиванием —
это параметр GitHub Contents API. В git CLI операция называется `git update-ref`,
через дефис. Инструкция адресована не моему инструменту.

**Проблема 2 — «блокировка» не существует.** У меня нет «blocked ref update».
Есть `git update-ref`, `git branch -f`, `git switch -c`. Ни одна не
«блокируется» в том смысле, который подразумевает текст.

**Проблема 3 — процедура создаёт риск для рабочей копии.** Раздел описывает
создание временных веток в **том же** репозитории, где идёт работа. Для меня это
означает: фикстуры появляются в моём рабочем дереве, в `git status`, в ветках,
которые можно случайно закоммитить или запушить.

**Доказательство опасности смешения.** Проверка на локальном репозитории:

```
before: a.txt = 'PRECIOUS UNCOMMITTED'
$ git reset --hard HEAD
after : a.txt = 'committed'        ← незакоммиченная работа потеряна
untracked survived: True           ← но untracked уцелел
```

Именно поэтому инструкции уровня «перемести ref, потом откатись» для агента с
реальным git опаснее, чем для API-клиента: у API-клиента нет незакоммиченного
рабочего дерева, а у меня есть.

**Что делать.** Раздел должен переехать в host-specific часть и быть
сформулирован через мой механизм: одноразовая ветка от известного SHA, **в
отдельном clone/worktree**, не в рабочем дереве. Либо `git worktree add`, либо
`git clone` во временный каталог — тогда рабочий checkout физически не затрагивается.

### 2.3 §7 GitHub Connector-specific mechanics

Раздел честно помечен как механика Connector, и это правильно. Но он находится
**внутри** canonical owner и без явного адресата — «these are mechanics of the
Connector path». Для агента, который читает файл целиком, это шум: blob SHA как
write precondition мне не нужен, `write`/`edit` работают иначе.

Не вредно, но занимает место в файле, который я обязан читать при каждой
repository-операции. Кандидат на вынос или на явную пометку «не для Agentic AI».

### 2.4 §3 Taxonomy: `prototypes/` объявлен, но отсутствует

Скилл описывает `prototypes/` как категорию содержимого.

**Доказательство:**

```
references/   True
prototypes/   False      ← каталога нет
docs/         True
```

Категория описана, но в репозитории её нет. Для канонического владельца это
терпимо (таксономия шире текущего состояния), но стоит отметить: описание
категории, которой никогда не было, читается как факт о репозитории.

### 2.5 Самоописание устарело: файл называет себя «rule»

После переноса `.ai/rules/` → `.ai/skills/` текст не обновлён.

**Доказательство (файл `.ai/skills/repository/SKILL.md`):**

```
line  95: this rule defines the repository-level durability …
line 134: … rather than in generic active rules unless they define a reusable invariant.
line 203: repository-wide rule as a second implementation procedure.
```

Файл — скилл (`name: repository`), но называет себя «rule». Это не косметика:
`.ai/skills/workflow/SKILL.md` ссылается на «the canonical repository owner», а
сам владелец говорит о себе в третьем лице как о правиле. Формально ничего не
ломается, но это след миграции, который стоит убрать.

### 2.6 Нормативный язык: одно нарушение

По `.ai/skills/normative-language/SKILL.md` (BCP 14 + `DO`/`DO NOT`):

```
line 78: Never commit:            ← запрет без MUST NOT
line 129: … inspection may be batched as:   ← ordinary English, нарушения нет
```

`Never commit:` — раздел §4. Это нормативный запрет, выраженный не по канону.
По правилу §6 «Express prohibitions explicitly» должно быть `MUST NOT commit`
или введено через `DO NOT`. Пункт мелкий, но правило применяется к самому
владельцу.

## 3. Чего не хватает

### 3.1 Различения remote и local как **двух механик**, а не одного свода

Сейчас файл смешивает три разных механизма в одном тексте:

- GitHub Contents API (blob SHA, complete-content replacement);
- локальный git (working tree, index, refs);
- абстрактные инварианты (read-back, diff, scope).

Третий нужен всем. Первые два — взаимоисключающие. Пока они в одном файле, агент
не может отличить «инструкция для меня» от «инструкция для другого хостa».

**Предлагаемая структура** (не диктую, предлагаю):

```
repository/SKILL.md            общие инварианты + границы + taxonomy + durability
  └ host-mechanics/            или разделы внутри:
      remote-api.md            blob SHA, complete-content, update_ref
      local-git.md             working tree, index, refs, worktree-фикстуры
```

### 3.2 Явного адресата у host-specific разделов

Ни один раздел не говорит «это для Conversational AI» или «это для Agentic AI».
Формулировка «MAY use different mutation mechanisms» слишком мягкая: она
описывает возможность, а не разграничивает применимость. Нужен явный маркер
адресата — тогда агент может пропустить чужой раздел, а не примерять его на себя.

### 3.3 Правила про игнорируемые артефакты

Для меня существуют файлы, которых **нет в git вообще**: gitignored адаптеры,
локальные конфиги, generated output.

**Доказательство:**

```
git ls-files .agents            -> 0 entries
actual .agents/skills dirs      -> 9
git status --porcelain          -> 0 entries       (ignored невидим)
git status --porcelain --ignored -> 1 entry
```

То есть «список файлов репозитория» и «состояние рабочей копии» — **разные
множества**. Владелец repo-семантики об этом не говорит ни слова. Для агента это
реальный источник ошибок: проверка «файла нет в `git ls-files`» не означает, что
файла нет.

### 3.4 Правила про состояние рабочей копии vs коммит

У API-клиента нет незакоммиченных изменений. У меня есть, и они — нормальное
рабочее состояние. Владелец не описывает:

- что делать с незакоммиченными изменениями перед операцией;
- когда обязательно остановиться, а не «откатиться»;
- что `reset --hard`/`checkout --force` уничтожают работу (см. доказательство §2.2).

Инвариант «read back» есть, но он про запись, а не про защиту уже
существующей незакоммиченной работы.

## 4. Что мне нравится

- **§7 целиком.** Это лучший раздел: он отделяет инварианты от механики и прямо
  говорит, что host-enforcement не заменяет независимую проверку результата.
- **§6.1.** Чёткое разделение active/supporting и запрет активному владельцу
  зависеть от supporting-слоя. Работает и для меня.
- **§5.** «Conversation history is temporary working context» — верно и полезно.
- **Принцип из §7.** «host-specific mechanisms MUST NOT be copied into this
  repository-wide rule as a second implementation procedure» — именно этот
  принцип и нарушен остальным текстом. Если применить его ко всему файлу,
  получится ровно то разделение, которого не хватает.

## 5. Предлагаемые действия

| Приоритет | Действие | Обоснование |
|---|---|---|
| Высокий | Разделить host-specific механику по адресату: remote API против local git | §2.1, §2.3, §3.1; сейчас инструкции чужого механизма читаются как мои |
| Высокий | Переработать §8: фикстуры вне рабочего дерева (`git worktree`/отдельный clone) | §2.2; процедура создаёт риск для незакоммиченной работы |
| Средний | Добавить раздел про игнорируемые/untracked артефакты | §3.3; `git ls-files` не описывает рабочую копию |
| Средний | Добавить правила про незакоммиченное состояние | §3.4; у меня оно есть, у API-клиента нет |
| Низкий | Убрать самоописание «rule» → «skill» | §2.5 |
| Низкий | `Never commit:` → по канону нормативного языка | §2.6 |
| Низкий | Уточнить статус `prototypes/` | §2.4 |

## 6. Границы этого отчёта

- Оценка сделана для среды **DSH с локальной рабочей копией git** и не
  претендует на роль инструкции для Conversational AI.
- Проверено на редакции `a0fbc8d`. При расхождении с текущим `SKILL.md`
  приоритет у владельца.
- Утверждения про отсутствие/наличие файлов и каталогов подтверждены командами
  из этой сессии; цитаты — из прочитанного файла.
- Что именно изменится в владельце — решение пользователя. Этот документ
  фиксирует наблюдения и предложения, а не выполняет миграцию.

blocked») убрана; общий принцип отказа от одного механизма сохранён в
host-нейтральной формулировке.

внутри отдельного `git worktree` не затронул незакоммиченное изменение основного
рабочего дерева.
